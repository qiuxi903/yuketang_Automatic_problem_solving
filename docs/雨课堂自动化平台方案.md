# 雨课堂自动化做题平台 · 方案设计（v0.2）

> v0.2 已并入你的四项决策：多用户平台 + 每次扫码、Agent 用 Python、首期即多账号并发、答案库走「先采集再导入」。

## 一、目标与定位

做一个真正的多用户平台：用户注册并登录平台账号（这个账号是固定的），做题时每次用手机扫一次码登录雨课堂（雨课堂账号不固定，谁扫就做谁的）。扫码后平台读取该账号实际作业，由用户确认答案库批次，再把该批次试卷全部做完并提交，前端实时显示进度与成绩。

首期即支持多账号并发：多个用户同时提交任务，各自独立会话、互不干扰。

不做：不破解验证码、不做风控绕过、不直接改雨课堂服务端数据，只走正常前端交互。

## 二、已确认的决策

1. 部署范围：多用户服务器部署，MySQL 持久化，平台账号固定、雨课堂账号每次扫码
2. Agent 执行器：Python（Playwright），直接复用 match_idx.py 与 verify2.py
3. 首期范围：直接做多账号并发
4. 答案库：先在测试平台做一次题拿到完整答案，再导入平台

## 三、已有资产（可直接复用）

- 规则：`雨课堂答题AI提示词.md`（9 条铁律）
- 答案库：`答案库/10-01/*.md`，30 套 1626 题，格式为「题干 + 答案文本」
- 匹配器：`match_idx.py`（题干定位到选项索引，含归一化、相似度、选项前缀剥离、正负号匹配）
- 校验器：`verify2.py`（作答结果与答案库比对）
- 索引缓存：`idx.json`（试卷名到选项索引数组）
- 页面样本：`dom_{examId}.json`（30 套题目 DOM 快照）

结论：匹配与校验算法已成熟且满分验证过，平台化主要是把它变成服务，补上「扫码会话 + 浏览器执行 + 并发编排 + 进度推送 + 答案采集闭环」。

## 四、总体架构

五个组成部分

1. 前端（Vue3）：注册登录、发起任务、扫码、实时进度、成绩汇总、答案库管理
2. 后端（Spring Boot 3.2）：平台账号与 JWT、课程与试卷元数据、任务编排与调度、WebSocket 推送、答案库存储
3. Agent 集群（Python + Playwright）：无头 Chromium，负责登录、抓题、作答、交卷、采集答案
4. 匹配与校验服务（Python FastAPI）：复用 match_idx.py 与 verify2.py
5. 采集服务（Python）：交卷后从结果页抓取正确答案，回写答案库

存储

- MySQL：平台用户、课程、试卷、题目、答案库、任务、成绩
- Redis：雨课堂会话 Cookie、任务队列、IDX 缓存、进度快照、限流计数

数据流

前端发起任务 → 后端落库入队 → Redis 队列 → 空闲 Agent 领取 → 驱动浏览器操作雨课堂 → 结果与进度回写 MySQL 与 Redis → WebSocket 推送 → 前端展示

## 五、核心流程

### 5.1 平台账号

- 注册与登录走平台自己的账号体系，JWT 鉴权
- 平台账号固定，与雨课堂账号无绑定关系
- 用户数据（任务、成绩、答案库贡献）都挂在平台账号下

### 5.2 每次扫码登录雨课堂（会话生命周期）

1. 用户点「开始做题」，后端分配 sessionId，调度一个 Agent 启动浏览器打开雨课堂登录页
2. Agent 截取二维码，前端轮询或经 WebSocket 拿到图片展示
3. 用户用微信或雨课堂 App 扫码确认
4. Agent 检测登录成功，导出 Cookie 与 localStorage，加密写 Redis（TTL 取考试时长上限）
5. 该会话可连续完成该雨课堂账号下的多套试卷；任务结束或超时后释放会话

要点：二维码有时效，需自动刷新；会话过期要能提示重新扫码；同一时刻同一雨课堂账号只允许一个会话在跑。

### 5.3 试卷同步与识别

- 拉取课程学习日志或考试列表，得到试卷名、examId、满分、状态（未作答或得分）
- 为每套试卷生成「指纹」（题干集合 hash），用于识别内容相同的重复试卷（如 202615 与 202615（2））

### 5.4 答案采集（首次遇到新卷，闭环关键）

这是你要求的「先做一次题拿到完整答案再导入」的平台化落地，做成自动化闭环

1. 平台对答案库里没有的试卷，标记为「待采集」
2. 采集时先用现有答案库加 AI 兜底作答并交卷
3. 交卷后从结果页或结果接口抓取每题的正确选项文本
4. 按标准格式写入答案库（题干 + 答案文本），回写 MySQL 与 MD 文件
5. 下次再做该卷（含重复卷）直接命中答案库，稳定满分

要点：采集一次，长期复用；选项顺序会被打乱，答案一律存文本而非字母。

### 5.5 自动作答

1. 取未作答试卷，按 examId 打开考试入口，点「开始」
2. 抓取题目 DOM（题干与选项文本）
3. 调匹配服务：指纹命中答案库则直接取 IDX；未命中则现场匹配生成 IDX 并回写
4. 按 IDX 点击选项（`.el-radio`）
5. 提交前调校验服务与答案库比对，全部一致才交卷
6. 交卷：header 交卷按钮，确认弹窗，交卷
7. 从成绩页抓取得分并落库

### 5.6 并发与任务编排

- 任务粒度：平台账号 + 雨课堂会话 + 批次
- Agent 池：N 个 Worker，每个 Worker 持有独立浏览器上下文，从队列领取任务
- 并发规则：同一雨课堂会话内串行；不同用户、不同会话之间并行
- 限流：单会话答题频率控制，避免触发风控
- 失败处理：单卷失败自动重试，两次失败标记人工介入并回退

### 5.7 实时进度

- WebSocket 推送：当前试卷、题号进度、每套得分、总体进度
- 断线重连后从 Redis 快照恢复

## 六、数据模型（MySQL）

- user：平台用户（id, username, password_hash, role, created_at）
- ykt_session：雨课堂会话（id, user_id, ykt_name, session_key, status, expire_at）
- course：课程（id, ykt_course_id, name）
- paper：试卷（id, name, exam_id, total, fingerprint, batch, source）
- question：题目（id, paper_id, seq, stem, stem_norm, answer_text, collected）
- task：任务（id, user_id, ykt_session_id, batch, mode, status, total_paper, done_paper, created_at）
- task_item：任务明细（id, task_id, paper_id, exam_id, status, score, idx_json, sel_json, error）
- task_log：执行日志（id, task_item_id, level, message, created_at）

说明：paper 的 source 区分「导入」与「采集」；question 的 collected 标记该题答案是否已由采集闭环确认。

## 七、接口草案

认证

- POST /api/auth/register
- POST /api/auth/login 返回 JWT

雨课堂会话

- POST /api/sessions 返回 sessionId 与二维码
- GET /api/sessions/{id}/qrcode 返回二维码图片
- GET /api/sessions/{id}/status 返回扫码状态
- DELETE /api/sessions/{id} 释放会话

课程与试卷

- GET /api/courses
- GET /api/courses/{id}/papers

任务

- POST /api/tasks 传入 batch 与 mode（answer 或 collect），返回 taskId
- GET /api/tasks/{id}
- POST /api/tasks/{id}/pause
- WS /ws/tasks/{id}

答案库

- GET /api/papers/{id}/answers
- POST /api/papers/{id}/answers
- POST /api/papers/{id}/collect 触发采集

## 十一、风险与注意事项

- 二维码时效与会话过期：需自动刷新与重新扫码机制
- 多用户并发下的资源占用：浏览器实例吃内存，需限制 Agent 池规模并做好回收
- 自动化检测：保持真实浏览器环境、控制频率、避免同账号高频
- 答案准确性：选项顺序会被打乱，必须按文本匹配，沿用现有铁律；最终以平台判定为准
- 安全：雨课堂 Cookie 属敏感凭据，需加密存储、最小权限、可随时释放
- 合规：仅限本人账号或已授权范围使用
